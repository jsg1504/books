Chapter 05

공유 상태와 블랙보드

메시지는 한 에이전트에서 다른 에이전트로 흐른다. 다른 길도 있다. 모두가 읽고 쓰는 공유 공간을 하나 두고, 에이전트들이 거기에 결과를 올리고 거기서 필요한 것을 가져가는 것이다. 파일 시스템, 데이터베이스, 작업 목록, 문서가 모두 공유 상태가 될 수 있다. 공유 상태는 전언 게임의 손실을 없애고 리더가 죽어도 일을 이어 가게 해 주지만, 여럿이 동시에 같은 것을 고칠 때 새로운 버그를 만든다.

  • 블랙보드 아키텍처의 세 요소(칠판, 지식원, 제어)를 설명할 수 있다.
  • 여러 에이전트가 같은 상태를 읽고-고치고-쓸 때 생기는 갱신 손실을 설명하고, 잠금과 낙관적 동시성 제어로 막을 수 있다.
  • 대화 전체, 요약, 아티팩트 중 무엇을 공유할지 토큰과 일관성으로 따질 수 있다.
  • 상태를 에이전트 바깥에 두어 장애에서 복구하는 설계를 설명할 수 있다.

블랙보드 아키텍처

블랙보드blackboard는 1970년대 음성 인식 시스템 Hearsay-II에서 나온 오래된 구조다. 여러 전문가가 칠판 하나를 둘러싸고 서 있다고 상상하자. 누군가 칠판에 가설을 쓰면, 그것을 다룰 줄 아는 전문가가 나서서 근거를 덧붙이거나 반박한다. 아무도 다음에 누가 말할지 정하지 않는다. 칠판의 상태가 다음 행동을 부른다.

해볼 것: ① 검증자를 끄고 틀린 가설 비율을 0.6으로 올려 보자. 작성자는 검증 없이 근거만 붙은 가설을 그대로 답에 쓴다. ② 검증자를 켜면 행동 수는 늘지만 틀린 가설이 걸러진다. ③ 제어 방식을 유망한 가설 우선으로 바꾸면 근거가 많이 붙은 가설부터 처리해 답이 더 빨리 나온다. 블랙보드에서도 “누가 먼저 나설까”는 설계 대상이다.

동시에 고치면 생기는 일

공유 상태의 대가는 동시성이다. 두 에이전트가 같은 작업 목록 파일을 고친다고 하자. 둘 다 파일을 읽고, 각자 몇 초에서 수십 초 동안 생각한 뒤(모델 호출), 고친 내용을 통째로 쓴다. 나중에 쓴 쪽이 먼저 쓴 쪽의 변경을 덮어쓴다. 이것이 갱신 손실lost update이고, 원인은 경쟁 조건race condition이다. LLM 에이전트는 읽기와 쓰기 사이가 길어서 이 문제가 일반 프로그램보다 훨씬 자주 일어난다.

해볼 것: ① 보호 없음에서 생각 시간을 3초에서 30초로 올려 보자. 사라지는 변경이 두세 개에서 대부분으로 늘어난다. 실행 기록에는 모두 “저장 완료”로 남는다는 것이 더 무섭다. ② 잠금은 손실이 없지만, 한 에이전트가 생각하는 동안 나머지가 기다려(보라) 전체 시간이 크게 늘어난다. ③ 버전 확인은 쓰기 직전에 “내가 읽은 뒤 바뀌었나?”만 본다. 바뀌었으면 거절하고 다시 읽게 한다. 생각 시간이 짧아 충돌이 드물면 기다림 없이 끝나지만, 생각 시간이 길어 충돌이 잦으면 거절과 재시도가 쌓여 잠금보다도 느려진다. ④ 그래서 더 근본적인 해법은 같은 것을 고치지 않게 나누는 것이다(파일·항목 단위 소유권, 3장의 범위).
낙관적 동시성 제어로 쓰는 도구pseudo
def update_todo(path, new_text, read_version):
    cur = store.get(path)
    if cur.version != read_version:
        return "충돌: 읽은 뒤 다른 에이전트가 고쳤습니다 (v{read}→v{cur}). 다시 읽고 병합하세요."
    store.put(path, new_text, version=cur.version + 1)
    return "저장됨 v{cur.version + 1}"

무엇을 공유할까

에이전트들이 서로의 무엇을 볼 수 있게 할지는 스펙트럼이다. 한쪽 끝은 모든 에이전트가 전체 대화 기록을 공유하는 것이다. 서로의 결정을 다 알기 때문에 어긋나지 않지만, 창이 빨리 차고 하위 에이전트를 쓰는 이유(격리)가 사라진다. 다른 끝은 최종 요약만 공유하는 것이다. 가볍지만 서로 모르는 결정이 충돌한다. 그 사이에 결정 기록과 아티팩트를 공유하는 방법이 있다. 대화 전체 대신 “지금까지 정한 것”과 “만든 것”만 칠판에 남긴다.

상태는 에이전트 바깥에

2장에서 리더는 단일 장애점이었다. 리더의 계획과 진행 상황이 리더의 컨텍스트 안에만 있으면, 리더가 멈추는 순간 모두 사라진다. 계획, 위임 기록, 각 워커의 상태, 만들어진 아티팩트를 바깥 저장소에 두면 새 리더가 그것을 읽고 이어 갈 수 있다. 장시간 돌아가는 시스템에서는 리더의 컨텍스트가 넘쳐 새로 시작해야 할 때도 같은 원리로 이어 간다.

핵심 정리

  1. 블랙보드는 칠판(공유 상태), 지식원(에이전트), 제어기로 이뤄진다. 칠판의 변화가 다음 행동을 부르므로 누가 나설지 미리 정하지 않아도 된다.
  2. 읽고-생각하고-쓰는 사이가 긴 LLM 에이전트는 경쟁 조건에 특히 약하다. 잠금은 안전하지만 느리고, 버전 확인은 충돌이 드물 때 빠르다. 가장 좋은 것은 소유권을 나눠 충돌 자체를 없애는 것이다.
  3. 대화 전체 공유는 창을 터뜨리고, 요약만 공유하면 결정이 어긋난다. 결정 기록과 아티팩트를 공유하는 것이 대개 최선이다.
  4. 계획과 진행 상황을 에이전트 바깥에 두면 리더를 다시 띄워 이어 갈 수 있다.

확인 퀴즈

1. 블랙보드 구조에서 “다음에 어떤 에이전트가 일할지”를 정하는 것은?

에이전트는 자신이 다룰 수 있는 항목이 칠판에 나타나면 나선다. 여럿이 나서려 하면 제어기가 고른다.

2. 두 에이전트가 같은 문서를 각자 읽고 30초 뒤 통째로 저장했다. 둘 다 “저장 완료”를 받았는데 한쪽 변경이 없다. 원인은?

둘 다 같은 옛 버전을 읽고 고쳤기 때문이다. 버전 확인을 넣으면 두 번째 쓰기가 거절되고 다시 읽게 된다.

3. 충돌이 드물고 생각 시간이 긴 에이전트들에게 가장 알맞은 동시성 제어는?

잠금은 생각 시간 내내 다른 에이전트를 세운다. 충돌이 드물면 낙관적 방식이 거의 기다림 없이 손실을 막는다.

4. 프런트엔드와 백엔드 워커가 API 이름 규칙을 서로 다르게 정해 합칠 수 없었다. 무엇을 공유했어야 하나?

결정 기록은 짧고, 결정이 어긋나는 것을 막는다. 대화 전체는 너무 크고, 최종 요약은 너무 늦다.
