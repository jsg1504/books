Chapter 04

도구 설계: 에이전트-컴퓨터 인터페이스

사람을 위한 프로그램에 UI 설계가 있듯, 에이전트를 위한 도구에도 인터페이스 설계가 있다. 모델은 도구의 이름과 설명만 보고 무엇을 할지 고르고, 도구가 돌려준 텍스트만 보고 다음 행동을 정한다. SWE-agent 연구진은 이것을 에이전트-컴퓨터 인터페이스(ACI)라고 불렀고, 같은 모델에게 더 잘 설계된 도구를 주는 것만으로 성능이 오른다는 것을 보였다. 이 장에서는 도구 정의의 구조, 도구 개수의 함정, 긴 출력과 오류 메시지를 설계하는 법을 실험한다.

  • 도구 정의의 이름·설명·입력 스키마가 각각 모델의 어떤 결정에 쓰이는지 설명할 수 있다.
  • 도구를 늘릴수록 생기는 토큰 비용과 선택 오류를 이해하고, 지연 로딩(도구 검색)의 장단점을 말할 수 있다.
  • 긴 도구 출력을 자르거나 파일로 빼는 전략을 비교할 수 있다.
  • 모델이 스스로 회복할 수 있는 오류 메시지를 쓸 수 있다.

도구 정의의 해부

하네스는 모델에게 도구마다 세 가지를 알려 준다. 이름, 설명, 인자의 형태를 적은 입력 스키마input schema다. 모델은 이 정보만으로 “지금 이 도구를 쓸지”, “어떤 인자로 부를지”를 정한다. 설명은 모델이 읽는 문서이자 프롬프트다.

도구 정의 예시 (JSON)매 호출 입력에 포함
{
  "name": "edit_file",
  "description": "파일의 일부를 바꾼다. old_string은
    파일에서 정확히 한 번 나와야 한다. 여러 곳을
    바꾸려면 replace_all을 true로. 새 파일은
    write_file을 쓴다.",
  "input_schema": {
    "type": "object",
    "properties": {
      "path": {"type": "string",
               "description": "절대 경로"},
      "old_string": {"type": "string"},
      "new_string": {"type": "string"},
      "replace_all": {"type": "boolean",
                      "default": false}
    },
    "required": ["path", "old_string", "new_string"]
  }
}

설계 원칙을 몇 가지 정리하면 이렇다. ① 사람이 헷갈릴 도구는 모델도 헷갈린다. 이름과 설명만 보고 동료가 바로 쓸 수 있는지 상상해 보자. ② 실수를 형식으로 막는다. 상대 경로 때문에 실수가 잦았다면 절대 경로만 받게 바꾸는 식이다. ③ 낮은 수준의 API를 그대로 노출하지 않는다. 목록 조회, 상세 조회, 필터를 따로 주기보다 에이전트가 실제로 하려는 일(“이름으로 사용자 찾기”)을 한 번에 해 주는 도구가 호출 수와 토큰을 줄인다.

MCP: 도구를 연결하는 표준MCPModel Context Protocol는 도구와 데이터 소스를 하네스에 연결하는 개방형 프로토콜이다. 서버 하나를 만들면 여러 하네스에서 같은 도구를 쓸 수 있다. 다만 MCP 서버를 여러 개 붙이면 도구 정의가 순식간에 늘어나므로, 다음 절의 문제가 더 커진다.

몇 개의 도구를 줄까

도구가 많으면 할 수 있는 일이 늘지만 대가가 두 가지 있다. 첫째, 모든 도구 정의가 매 호출 입력에 들어간다. 도구 하나가 수백 토큰이면 수십 개만으로 수만 토큰이다. 둘째, 비슷한 도구가 많을수록 엉뚱한 것을 고를 확률이 오른다. 해결책 중 하나는 도구 검색tool search · deferred loading이다. 처음에는 검색 도구와 핵심 도구만 주고, 모델이 필요한 도구를 검색하면 그 정의를 불러온다. 대신 검색 한 번의 왕복과 검색이 빗나갈 위험이 생긴다.

오류 메시지는 다음 행동의 프롬프트다

도구가 실패하면 그 오류 텍스트가 모델이 받는 유일한 단서다. 사람 개발자는 “Error”만 보고도 로그를 뒤지겠지만, 모델은 받은 텍스트 안에서 다음 행동을 고른다. 좋은 오류 메시지는 무엇이 잘못됐는지, 왜인지, 어떻게 고칠 수 있는지를 담는다. 아래 게임에서 실패한 도구 호출마다 모델이 가장 빨리 회복할 오류 메시지를 골라 보자.

문제—
맞힘0
예상 회복 턴 합계 (선택한 메시지 기준)0
기준: 모델이 다음 호출 한 번으로 바로잡을 수 있는가? 스택 트레이스나 오류 코드만 있으면 모델은 추측으로 여러 번 시도하거나, 같은 실수를 반복한다(2장의 헛도는 루프).

핵심 정리

  1. 도구의 이름·설명·스키마는 모델이 읽는 인터페이스다. 사람이 헷갈릴 도구는 모델도 헷갈린다.
  2. 도구가 많을수록 매 호출 토큰이 늘고 선택 오류가 오른다. 많을 때는 도구 검색(지연 로딩)이 낫지만 검색 품질이 상한을 정한다.
  3. 긴 출력은 크기를 제한하고, 잘렸다는 사실과 전체를 다시 볼 방법(파일, 페이지)을 함께 알려 준다.
  4. 오류 메시지에는 무엇이, 왜, 어떻게 고칠지를 담는다. 오류 메시지가 곧 다음 행동의 프롬프트다.

확인 퀴즈

1. 에이전트가 search_users와 find_user 중 엉뚱한 것을 자주 고른다. 가장 먼저 할 일은?

선택 오류는 대부분 인터페이스 문제다. 겹치는 도구를 줄이고 설명을 고치는 것이 가장 싸고 효과적이다.

2. 도구 120개, 정의 하나 평균 400토큰. 모두 미리 로딩하면 매 호출 도구 정의만으로 대략?

120 × 400 = 48,000. 캐시가 비용을 줄여도 윈도우 공간과 선택 혼란은 남는다.

3. 빌드 로그가 5만 줄이다. 대부분의 경우 가장 쓸모 있는 기본 전략은?

빌드 오류는 대개 끝에 있다. 잘렸다는 사실과 전체를 볼 방법을 알려 주면 모델이 필요할 때 더 찾아본다.

4. 다음 중 모델의 회복에 가장 도움이 되는 오류 메시지는?

무엇이 빠졌는지, 무엇을 받았는지, 어떻게 고칠지를 모두 담았다. 다음 호출 한 번으로 고칠 수 있다.
