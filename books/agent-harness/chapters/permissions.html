Chapter 06

권한 · 훅 · 가드레일

모델이 고른 도구 호출은 실행되기 전에 하네스의 검문소를 지난다. 이 호출은 그냥 해도 되는가, 사람에게 물어야 하는가, 막아야 하는가. 검문소는 두 가지 부품으로 이루어진다. 선언적인 권한 규칙과, 수명 주기 곳곳에 끼워 넣는 프로그램인 훅이다. 이 장에서는 규칙이 어떤 순서로 평가되는지, 훅으로 무엇을 강제할 수 있는지, 그리고 “다 물어보면 안전하다”는 직관이 왜 틀리는지 실험한다.

  • allow · ask · deny 규칙이 겹칠 때 최종 결정이 정해지는 순서를 설명할 수 있다.
  • 셸 명령의 접두사 규칙이 복합 명령으로 우회되는 문제와 대책을 말할 수 있다.
  • 훅을 어느 수명 주기 이벤트에 걸지, 어떤 일(차단·변환·기록·되먹임)을 시킬지 설계할 수 있다.
  • 확인 요청의 빈도와 사람의 주의력 사이의 관계로 권한 모드를 비교할 수 있다.

권한 규칙의 평가 순서

권한 규칙은 보통 결정 도구(패턴) 꼴이다. 예를 들어 allow Bash(npm test*)는 “npm test로 시작하는 셸 명령은 묻지 않고 실행”, deny Read(**/.env)는 “어느 폴더의 .env든 읽기 금지”다. 한 호출에 여러 규칙이 걸리면 가장 엄격한 것이 이긴다. 아무 규칙에도 걸리지 않으면 하네스 전체의 권한 모드permission mode가 정한 기본값을 따른다.

훅: 수명 주기에 끼우는 코드

규칙은 패턴만 본다. 명령 안에 API 키가 들어 있는지, 편집한 파일이 포매터를 통과하는지, 작업을 끝내도 될 만큼 테스트가 통과했는지는 코드가 확인해야 한다. 이런 검사를 하네스의 수명 주기 이벤트에 끼워 넣은 것이 훅hook이다. 훅은 이벤트 정보를 입력으로 받고, 결과로 통과·차단·수정을 돌려준다. 차단할 때 사유를 함께 돌려주면 하네스는 그 사유를 모델에게 전달해 다음 행동을 바꾸게 한다.

모델의 행동
켜 둔 훅
해볼 것: ① 모든 훅을 끄고 각 행동을 실행해 보자. 무엇이든 통과한다. ② 비밀 스캐너는 규칙으로는 잡기 어려운 “명령 속 내용”을 검사한다. ③ 테스트 게이트는 Stop 이벤트에서 종료를 막고 사유를 모델에게 되먹인다. 모델의 “다 했습니다”를 하네스가 검증하는 방법이다. ④ 훅도 코드라 느리면 매 호출이 느려지고, 훅 자체가 실패할 때의 기본 동작(통과? 차단?)도 정해야 한다.

다 물어보면 안전할까: 승인 피로

가장 안전해 보이는 설정은 “모든 행동을 사람에게 묻기”다. 그러나 사람은 시간당 수십 번의 확인 창을 꼼꼼히 읽지 못한다. 확인이 잦아질수록 내용을 보지 않고 승인하는 승인 피로approval fatigue가 온다. 그러면 정작 위험한 한 번도 습관처럼 승인된다. 좋은 권한 설계는 확인을 드물고 의미 있게 만든다. 안전한 것은 규칙으로 자동 허용하고, 위험한 것은 규칙으로 막고, 나머지는 샌드박스 안에서 피해를 가두고, 정말 되돌릴 수 없는 일만 묻는다.

P(꼼꼼히 읽음) = 11 + (r / r0)²   ·   하루 사고 = 호출 수 × 위험 비율 × (1 − 막을 확률)
r: 시간당 확인 요청 수, r0: 사람이 집중을 유지할 수 있는 빈도. 이 식은 개념을 보이기 위한 모형이다. 핵심은 확인 요청이 많을수록 확인 한 번의 가치가 떨어진다는 것이다.

승인 피로 — 네 가지 권한 설계의 하루

하루 사고하루 확인 요청
모두 묻기 · 사고—
규칙 + 묻기 · 사고—
샌드박스 + 자동 · 사고—
가드 없음 · 사고—
해볼 것: ① 시간당 호출을 20으로 낮추면 “모두 묻기”가 가장 안전하다. 사람이 다 읽을 수 있기 때문이다. ② 호출을 200 이상으로 올리면 “모두 묻기”의 사고가 “가드 없음”에 가까워진다. ③ “샌드박스 + 자동”은 확인 요청이 거의 없으면서도 사고가 적다. 행동을 막는 대신 결과를 가두기 때문이다. 단 샌드박스 밖으로 나가는 일(배포, 메시지 전송)은 여전히 확인해야 한다.

핵심 정리

  1. 권한 규칙은 deny → ask → allow 순으로 평가해 가장 엄격한 결정을 고른다. 규칙에 없으면 권한 모드의 기본값을 따른다.
  2. 셸 명령의 접두사 allow는 &&, ;, | 로 이어 붙인 명령에 뚫린다. 복합 명령은 나눠서 각각 평가한다.
  3. 훅은 수명 주기 이벤트에 끼운 코드다. 내용 검사, 자동 포맷, 감사 기록, 종료 검증처럼 패턴으로 못 하는 일을 강제한다.
  4. 확인 요청이 잦으면 사람은 읽지 않고 승인한다. 안전한 것은 자동, 위험한 것은 차단, 나머지는 샌드박스로 가두고, 되돌릴 수 없는 일만 묻는다.

확인 퀴즈

1. 규칙이 allow Read(**)와 deny Read(**/.env)다. Read(app/.env)는?

엄격한 결정이 이긴다. 그래서 넓게 허용하고 좁게 막는 조합이 안전하다.

2. allow Bash(git status*)만 있을 때 git status; rm -rf ~가 통과한다. 근본 대책은?

패턴 하나로는 셸 문법을 다 막을 수 없다. 명령을 나눠 평가하고, 샌드박스로 피해를 가두는 것을 함께 쓴다.

3. “작업이 끝났다”고 하는 모델의 말을 테스트로 검증하려면 어느 이벤트에 훅을 걸까?

모델이 종료하려 할 때 테스트를 돌리고, 실패하면 종료를 막고 실패 내용을 되먹인다.

4. 시간당 150번 확인을 요청하는 설정이 위험한 이유는?

확인의 가치는 사람의 주의력에 달렸다. 확인을 드물게, 되돌릴 수 없는 일에만 쓰는 것이 더 안전하다.
