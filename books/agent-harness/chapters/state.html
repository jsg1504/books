Chapter 07

상태 · 세션 · 체크포인트

모델은 상태가 없지만 하네스는 상태투성이다. 대화 기록, 할 일 목록, 바뀐 파일, 실행 중인 프로세스, 지금까지 쓴 비용. 두 시간째 돌던 작업이 네트워크 오류로 죽었을 때 처음부터 다시 할지, 직전 지점에서 이어 갈지는 하네스가 상태를 어떻게 저장했느냐에 달렸다. 이 장에서는 체크포인트를 얼마나 자주 남길지, 되감기가 어디까지 가능한지, 재시도가 왜 위험할 수 있는지 실험한다.

  • 하네스가 저장해야 하는 상태의 종류와 각각의 저장 비용을 설명할 수 있다.
  • 장애율과 체크포인트 비용으로 적절한 체크포인트 간격을 계산할 수 있다.
  • 대화 되감기와 코드 되감기의 차이, 그리고 되감을 수 없는 외부 부작용을 구분할 수 있다.
  • 멱등 키로 재시도의 중복 실행을 막는 원리를 설명할 수 있다.

하네스가 들고 있는 상태

여기에 더해 하네스가 저장할 수 없는 상태가 있다. 이미 원격 저장소에 올린 커밋, 보낸 메시지, 호출한 결제 API. 이것들은 하네스 밖, 세상에 남는다. 3절에서 다룬다.

체크포인트 간격 정하기

긴 작업 중간에 프로세스가 죽거나 API 오류가 이어지면, 마지막 체크포인트 이후의 일은 다시 해야 한다. 체크포인트를 자주 남기면 잃는 일은 적지만 저장 비용이 쌓인다. 이 균형은 고성능 컴퓨팅에서 오래 연구된 문제이고, 장애가 드물 때 잘 맞는 근사식이 있다(Young의 공식).

k* ≈ √( 2C / λ )   ·   기대 시간 ≈ L + LC/k1 − λ(k/2 + R)
L: 작업에 필요한 단계 수, C: 체크포인트 한 번의 비용(단계 단위), λ: 단계당 장애 확률, R: 장애 후 다시 시작하는 비용, k: 체크포인트 간격. 장애 한 번에 평균 k/2 단계를 잃는다. 체크포인트가 없으면 장애마다 처음부터 다시 해야 해서 기대 시간이 작업 길이에 지수적으로 늘어난다.

되감기: 어디까지 되돌릴 수 있나

에이전트가 엉뚱한 방향으로 30분을 갔다면, 사용자는 “10분 전으로 돌아가서 다르게 해 봐”라고 하고 싶다. 하네스가 편집 직전의 파일 내용과 대화 위치를 체크포인트로 남겨 두었다면 가능하다. 되감기에는 세 가지가 있다. 대화만(코드는 둔 채 지시를 다시), 코드만(대화는 둔 채 파일을 원래대로), 둘 다. 하지만 어떤 행동은 하네스 밖의 세상을 바꿔서 되감기로 되돌릴 수 없다.

멱등성: 재시도해도 안전한 도구

도구 호출이 타임아웃으로 끝났다고 해서 실행이 안 된 것은 아니다. 서버는 요청을 처리했는데 응답만 돌아오는 길에 사라졌을 수 있다. 이때 하네스(또는 모델)가 다시 시도하면 이슈가 두 개, 결제가 두 번 생긴다. 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질을 멱등성idempotency이라고 한다. 읽기는 원래 멱등이고, 쓰기는 멱등 키idempotency key를 붙여 서버가 같은 요청을 알아보게 만든다.

핵심 정리

  1. 하네스 상태는 대화, 작업 공간, 실행 환경, 진행·회계로 나뉜다. 실행 환경은 저장보다 재현 가능하게 만드는 편이 쉽다.
  2. 체크포인트 간격은 비용과 손실의 균형이다. 장애가 드물면 k* ≈ √(2C/λ). 체크포인트가 없으면 긴 작업은 끝나지 않는다.
  3. 대화와 코드는 되감을 수 있지만 push·전송·결제 같은 외부 부작용은 되감을 수 없다. 그래서 그런 행동은 확인 대상이다.
  4. 타임아웃은 “실행 안 됨”이 아니다. 쓰기 도구는 멱등 키로 재시도를 안전하게 만든다.

확인 퀴즈

1. 단계당 장애 확률이 0.005, 체크포인트 비용이 단계 1개 분량이다. Young의 근사로 적절한 간격은?

√(2 × 1 / 0.005) = √400 = 20.

2. 대화와 코드를 모두 30분 전으로 되감았다. 그 사이 에이전트가 한 일 중 되돌아가지 않는 것은?

원격에 나간 변경은 하네스 밖의 상태다. 되돌리려면 revert 같은 새 행동이 필요하다.

3. 결제 API 호출이 타임아웃되었다. 하네스가 바로 재시도해도 안전하려면?

응답만 유실되었을 수 있다. 멱등 키가 있어야 두 번째 요청이 새 결제가 되지 않는다.

4. 실행 환경(설치한 패키지, 띄운 서버)을 재개 가능하게 만드는 가장 실용적인 방법은?

환경은 저장보다 재현이 싸다. 대화 기록과 설정 스크립트가 있으면 새 샌드박스에서 같은 상태를 다시 만들 수 있다.
