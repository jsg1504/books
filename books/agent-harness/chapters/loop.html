Chapter 02

에이전트 루프와 종료 조건

에이전트의 심장은 놀랄 만큼 작다. 모델을 부르고, 도구 호출이 있으면 실행해 결과를 붙이고, 다시 부른다. 이 while 루프 하나가 하네스의 뼈대다. 어려운 것은 루프를 도는 일이 아니라 언제 멈출지다. 이 장에서는 루프 한 바퀴를 메시지 단위로 따라가고, 턴 상한이 성공률과 비용을 어떻게 바꾸는지, 같은 행동을 반복하는 헛도는 루프를 어떻게 알아채는지 실험한다.

  • tool_use와 tool_result 블록이 대화 목록에 어떻게 쌓이는지 단계별로 설명할 수 있다.
  • stop_reason 값마다 하네스가 해야 할 일을 구분할 수 있다.
  • 턴 상한을 너무 낮거나 높게 잡을 때의 손해를 분포로 설명할 수 있다.
  • 헛도는 루프를 감지할 때 결과까지 비교해야 하는 이유를 말할 수 있다.

가장 작은 하네스

도구를 쓰는 에이전트는 모두 다음 구조를 가진다. 모델 응답에 도구 호출이 있으면 하네스가 실행하고, 그 결과를 tool_result로 대화에 붙인 뒤 다시 모델을 부른다. 모델이 도구 호출 없이 답을 끝내면 루프도 끝난다.

agent_loop.py — 실제로 동작하는 최소 하네스의 형태Python 의사 코드
def run(task, tools, max_turns=40):
    messages = [{"role": "user", "content": task}]
    for turn in range(max_turns):
        resp = client.messages.create(model=MODEL, system=SYSTEM,
                                      tools=[t.schema for t in tools], messages=messages)
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":          # end_turn, max_tokens, ...
            return resp
        results = []
        for block in resp.content:
            if block.type == "tool_use":
                out = execute(block.name, block.input)          # 권한 검사 + 샌드박스
                results.append({"type": "tool_result",
                                "tool_use_id": block.id, "content": out})
        messages.append({"role": "user", "content": results})
    raise TurnLimitExceeded(messages)                      # 하네스가 강제로 멈춘다

세 가지를 눈여겨보자. 첫째, 도구 결과는 사용자 역할의 메시지로 돌아간다. 모델 입장에서는 세상이 보낸 답장이다. 둘째, 모든 tool_use에는 id가 있고 결과는 tool_use_id로 짝을 맞춘다. 한 응답에 도구 호출이 여러 개면(병렬 호출) 결과도 모두 돌려줘야 한다. 셋째, 루프의 끝은 두 가지다. 모델이 스스로 끝내거나(end_turn), 하네스가 끊는다(턴 상한).

stop_reason과 종료 조건

모델 API는 응답마다 왜 생성이 끝났는지 알려 준다. 하네스는 이 값에 따라 다음 행동을 정한다. 이름은 API마다 조금씩 다르지만 의미는 비슷하다.

stop_reason뜻하네스가 할 일
tool_use모델이 도구 호출을 요청했다권한 검사 → 실행 → tool_result를 붙이고 다시 호출
end_turn모델이 할 말을 마쳤다루프 종료, 사용자에게 결과 전달
max_tokens출력 한도에 걸려 잘렸다이어서 생성하게 하거나, 한도를 늘리거나, 실패로 기록 — 성공으로 취급하면 안 된다
stop_sequence지정한 중단 문자열이 나왔다그 문자열의 약속에 따라 처리

모델이 끝내지 않을 때를 대비해 하네스는 자기만의 종료 조건도 가진다. 턴 상한, 토큰·비용 예산, 벽시계 시간, 사용자 중단, 헛도는 루프 감지다. 이 중 가장 기본인 턴 상한은 얼마로 잡아야 할까?

작업마다 필요한 턴 수는 제각각이고 오른쪽으로 꼬리가 긴 분포를 이룬다. 대부분은 금방 끝나지만 어떤 작업은 수십 턴이 필요하다. 여기에 일정 비율의 헛도는 실행(영원히 끝나지 않는 실행)이 섞여 있다고 하자. 상한 C를 두면 두 종류의 손해가 생긴다.

성공률 = (1 − q) · F(C)   ·   작업당 기대 턴 = (1 − q) · E[min(T, C)] + q · C
T: 정상 작업이 필요한 턴 수(로그정규분포로 모형화), F: T의 누적분포, q: 헛도는 실행의 비율. C가 작으면 정상 작업을 끊어 성공률을 잃고, C가 크면 헛도는 실행마다 C턴씩 낭비한다. “성공 한 건당 턴”이 가장 작은 지점이 비용 관점의 최적 상한이다.

헛도는 루프 감지

에이전트가 같은 파일을 계속 읽거나, 두 가지 수정 사이를 오가며 테스트를 반복하는 모습은 흔하다. 이런 헛도는 루프doom loop는 상한에 닿을 때까지 비용을 태운다. 하네스는 최근 행동 기록을 보고 이것을 일찍 알아챌 수 있다. 가장 단순한 방법은 “최근 W개의 행동 중 같은 것이 k번 이상 나오면 경고”다.

문제는 “같은 행동”의 정의다. 테스트 주도로 일하는 에이전트는 npm test를 정상적으로 열 번도 부른다. 다만 그 사이 코드가 바뀌어 결과가 매번 다르다. 반면 헛도는 루프는 호출도 같고 결과도 같다. 그래서 키에 결과 해시를 넣으면 정상 반복과 헛돌기를 구분할 수 있다.

SIMULATOR

헛도는 루프 감지기 — 무엇을 “같다”고 볼까

비교 키
해볼 것: ① 비교 키를 호출만으로 바꾸면 정상 테스트 주도 작업에서 거짓 경보가 울린다. ② 왕복 편집은 A→B, B→A를 오가므로 같은 편집이 두 칸 걸러 나온다. 창이 너무 작으면 놓친다. ③ k를 2로 낮추면 빨리 잡지만, 정상 작업의 우연한 반복까지 잡는다. 감지 후에는 루프를 바로 끊기보다 “같은 행동을 반복하고 있다”는 메시지를 넣어 모델이 방향을 바꿀 기회를 주는 하네스가 많다.

핵심 정리

  1. 하네스의 뼈대는 “호출 → 도구 실행 → tool_result 추가”를 반복하는 루프다. 도구 결과는 user 역할로, tool_use_id로 짝지어 돌려준다.
  2. stop_reason에 따라 행동이 갈린다. 특히 max_tokens를 정상 종료로 취급하면 작업이 조용히 실패한다.
  3. 턴 상한은 헛도는 실행의 비용을 묶지만, 너무 낮으면 정상 작업을 끊는다. 최적점은 작업 분포와 헛돌기 비율에 달렸다.
  4. 헛도는 루프는 “같은 호출 + 같은 결과”의 반복으로 감지한다. 호출만 비교하면 정상적인 반복 테스트를 오탐한다.

확인 퀴즈

1. 모델이 한 응답에서 도구 두 개를 호출했다. 하네스가 할 일은?

짝이 맞지 않는 tool_use가 남으면 API가 요청을 거부하거나 모델이 결과를 기다리며 혼란에 빠진다.

2. stop_reason이 max_tokens인 응답을 end_turn처럼 처리하면?

잘린 출력은 도구 호출이 반쯤 쓰였거나 답이 중간에 끊긴 상태다. 이어서 생성하거나 실패로 기록해야 한다.

3. 헛도는 실행이 하나도 없다면(q = 0), 턴 상한을 높이는 것의 비용은?

상한은 끝나지 않는 실행에서만 비용이 된다. 현실에는 헛도는 실행이 있으므로 상한이 필요하다.

4. 에이전트가 코드를 고칠 때마다 npm test를 부른다. 이를 헛돌기로 오탐하지 않으려면?

테스트 결과가 매번 다르면 진전이 있다는 뜻이다. 결과까지 같아야 진짜 헛돌기다.
