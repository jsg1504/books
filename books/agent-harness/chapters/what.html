Chapter 01

하네스란 무엇인가

언어 모델 API가 하는 일은 하나다. 텍스트를 받아 텍스트를 돌려준다. 파일을 읽지도, 명령을 실행하지도, 어제 하던 일을 기억하지도 못한다. 그런데도 우리는 “에이전트가 버그를 고쳤다”고 말한다. 그 사이를 메우는 것이 모델을 감싼 프로그램, 하네스다. 이 장에서는 하네스가 어떤 층으로 이루어지는지 해부하고, 같은 모델이 하네스에 따라 얼마나 다른 에이전트가 되는지 실험으로 확인한다.

  • 모델 API의 입출력과 에이전트의 행동 사이에 하네스가 하는 일을 설명할 수 있다.
  • 하네스의 층(루프, 컨텍스트, 도구, 실행 환경, 권한, 상태)을 구분하고 각 층이 막는 실패를 말할 수 있다.
  • 같은 모델이라도 하네스 구성에 따라 성공률·비용·사고율이 크게 달라지는 이유를 설명할 수 있다.
  • “판단은 모델, 강제는 하네스” 원칙으로 책임을 나눌 수 있다.

모델은 글자를 받아 글자를 낸다

모델에게 “테스트가 왜 실패하는지 찾아서 고쳐 줘”라고 보내면, 모델은 npm test를 실행할 수 없다. 대신 “npm test를 실행하고 싶다”는 구조화된 요청을 텍스트로 출력할 뿐이다. 그 요청을 읽어 실제로 명령을 실행하고, 결과를 다음 입력에 붙여 다시 모델을 부르는 코드가 있어야 비로소 일이 진행된다. 이 코드 전체를 하네스harness라고 부른다. 벤치마크 문헌에서는 스캐폴드scaffold라고도 한다.

가장 작은 하네스의 뼈대 (의사 코드)2장에서 한 줄씩 해부한다
messages = [user("테스트를 고쳐 줘")]
while turns < MAX_TURNS:                     # 종료 조건 (2장)
    resp = model(system, tools, messages)      # 입력 조립 (3장) · 도구 정의 (4장)
    messages.append(resp)
    if resp.stop_reason != "tool_use": break
    for call in resp.tool_calls:
        if not permitted(call): result = denied(call)   # 권한 · 훅 (6장)
        else: result = sandbox.run(call)               # 실행 환경 (5장)
        messages.append(tool_result(call.id, result))
    checkpoint(messages)                       # 상태 (7장)

하네스 해부도

위 뼈대의 각 줄은 실제 제품에서 수천 줄짜리 하위 시스템이 된다. 아래 그림은 이 책이 쓰는 하네스의 지도다. 가운데에 모델이 있고, 바깥으로 갈수록 모델의 출력이 세상에 닿기 전에 거치는 층이다. 고리를 눌러 각 층이 하는 일과, 그 층이 없을 때 생기는 실패를 확인해 보자.

VISUALIZER

하네스 해부도 — 층을 눌러 보세요

층마다 없으면 생기는 실패를 눈여겨보자. 하네스 설계는 대부분 “모델이 언젠가 틀릴 것”을 전제로, 틀렸을 때 피해를 줄이고 다시 바로잡을 기회를 주는 일이다.

같은 모델, 다른 하네스

코딩 에이전트 벤치마크의 순위표를 보면 같은 모델 이름이 여러 번 등장한다. 모델은 같은데 감싼 하네스(도구 구성, 피드백 방식, 재시도, 컨텍스트 관리)가 다르기 때문이고, 그 차이만으로 해결률이 크게 벌어지는 일이 흔하다. 모델을 바꾸지 않고도 하네스를 고쳐서 얻을 수 있는 몫이 크다는 뜻이다.

아래 실험은 같은 “모델”(단계마다 일정 확률로 실수하는 단순 모형)에게 200개의 작업을 맡긴다. 하네스 부품을 하나씩 켜고 끄며 결과가 어떻게 바뀌는지 보자. 작업과 실수는 같은 난수 씨앗으로 만들어지므로 부품만 바뀐 비교다.

판단은 모델, 강제는 하네스

하네스를 설계할 때 가장 자주 하는 질문은 “이건 프롬프트에 쓸까, 코드로 막을까?”다. 기준은 단순하다. 틀려도 다시 시도하면 되는 판단은 모델에게 맡긴다. 어떤 파일을 열지, 테스트 실패의 원인이 무엇인지, 커밋 메시지를 어떻게 쓸지. 반대로 한 번이라도 틀리면 안 되는 규칙은 하네스 코드로 강제한다. 비밀 키 유출, 되돌릴 수 없는 삭제, 비용 한도, 컨텍스트 한도. 프롬프트에 “절대 하지 마”라고 쓰는 것은 확률을 낮출 뿐 0으로 만들지 못한다.

기준: 틀려도 다음 턴에 바로잡을 수 있는가? 그렇다면 모델에게. 한 번의 실수가 되돌릴 수 없는 피해나 한도 초과로 이어지는가? 그렇다면 하네스 코드로.

핵심 정리

  1. 모델은 텍스트를 받아 텍스트(행동 제안 포함)를 낼 뿐이다. 입력 조립, 실행, 결과 되먹임, 종료 판단은 모두 하네스의 일이다.
  2. 하네스는 루프·컨텍스트·도구·실행 환경·권한·상태의 층으로 나눌 수 있고, 각 층은 서로 다른 실패를 막는다.
  3. 같은 모델도 하네스에 따라 성공률, 비용, 사고율이 크게 달라진다. 모델 교체 없이 하네스 개선으로 얻는 몫이 크다.
  4. 틀려도 회복 가능한 판단은 모델에게, 한 번도 틀리면 안 되는 규칙은 하네스 코드로 강제한다.

확인 퀴즈

1. 모델이 tool_use: bash {"cmd":"ls"}를 출력했다. 실제로 ls를 실행하는 주체는?

모델의 도구 호출은 구조화된 텍스트일 뿐이다. 실행 여부, 실행 장소, 결과 전달은 하네스가 정한다.

2. 같은 모델을 쓰는 두 에이전트의 벤치마크 점수가 크게 다르다. 가장 그럴듯한 설명은?

모델은 같아도 하네스가 다르면 다른 에이전트다. 순위표가 “에이전트 + 모델” 조합으로 기록되는 이유다.

3. “하루 비용이 50달러를 넘으면 멈춘다”는 규칙은 어디에 두는 것이 맞을까?

모델은 자기 비용을 정확히 알 수 없고, 프롬프트는 확률을 낮출 뿐이다. 한도는 결정적으로 강제해야 한다.

4. 턴 상한을 두는 가장 직접적인 효과는?

상한은 헛도는 실행을 끊어 비용을 지킨다. 너무 낮으면 오히려 정상 작업을 끊어 성공률을 낮춘다(2장).
