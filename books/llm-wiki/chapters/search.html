Chapter 07

검색 도구: grep에서 하이브리드까지

페이지가 스무 개면 색인 한 장으로 충분하다. 이백 개도 대개 괜찮다. 이천 개가 되면 색인만으로 컨텍스트가 버거워진다. 그때 필요한 것이 검색 도구다. 그런데 어떤 검색일까? 정확한 단어를 찾는 키워드 검색, 뜻이 비슷한 문서를 찾는 임베딩 검색, 그 둘을 합친 하이브리드. 이 장에서는 예제 위키에 세 가지를 실제로 돌려 보고, 각각이 이기는 질문과 지는 질문을 찾고, 색인 하나로 버틸 수 있는 규모를 계산한다.

  • BM25 점수를 구성하는 단어 빈도, 역문서 빈도, 길이 정규화를 설명할 수 있다.
  • 키워드 검색과 임베딩 검색이 각각 강한 질문의 종류를 구별할 수 있다.
  • 역순위 융합으로 두 결과를 합치고, 위키 규모에 맞는 검색 방식을 고를 수 있다.

검색의 사다리

위키의 검색은 사다리처럼 한 칸씩 올라간다. 맨 아래는 색인 읽기다. 에이전트가 index.md를 읽고 고른다. 다음은 grep이다. 코딩 에이전트들이 임베딩 색인 없이 grep과 파일 목록만으로 큰 코드베이스를 잘 탐색하는 것처럼, 정확한 용어가 있으면 grep은 놀랄 만큼 강하다. 그다음이 BM25BM25, 단어가 드물수록, 자주 나올수록 점수를 주되 긴 문서는 깎는 고전적인 키워드 점수다. 그 위가 임베딩 검색embedding search, 단어가 달라도 뜻이 가까우면 찾는다. 맨 위가 둘을 합치는 하이브리드 검색hybrid search과 결과를 LLM이 다시 매기는 재순위화다. 카파시의 메모도 위키가 커지면 마크다운 폴더에 하이브리드 검색과 재순위화를 붙이는 로컬 검색 엔진(예: qmd)을 권한다.

BM25(D, Q) = Σq∈Q IDF(q) · f(q,D) · (k1 + 1)f(q,D) + k1 · (1 − b + b · |D| / avgdl)
IDF(q) = ln(1 + (N − nq + 0.5) / (nq + 0.5))
f(q,D): 문서 D에 단어 q가 나온 횟수, |D|: 문서 길이, avgdl: 평균 문서 길이, N: 문서 수, nq: q가 나온 문서 수. k1은 반복 출현의 포화 속도(보통 1.2~2.0), b는 길이 정규화 세기(보통 0.75). 한국어는 조사가 붙으므로 아래 실험은 한글을 두 글자씩 겹쳐 자른 바이그램으로 센다.

세 가지 검색을 직접 돌려 보기

아래 검색창은 예제 위키 18페이지 위에서 실제로 동작한다. 왼쪽은 BM25, 가운데는 장난감 임베딩, 오른쪽은 둘의 역순위 융합이다. 진짜 임베딩 모델을 브라우저에 넣을 수는 없으니, 장난감 임베딩은 손으로 만든 8차원 주제 벡터(검색, 지식 베이스, 컨텍스트, 순위, 역사, 도구, 인물, 메모)를 쓴다. 질의의 단어를 작은 동의어 사전으로 주제에 대응시키고 코사인 유사도로 순위를 매긴다. 원리는 같다. 단어가 아니라 뜻의 방향을 비교한다.

점수 대신 순위를 더하라

두 검색 결과를 합칠 때 점수를 그냥 더하면 안 된다. BM25 점수는 0에서 20을 넘나들고 코사인 유사도는 0에서 1 사이다. 단순 합은 사실상 BM25 순위가 된다. 점수를 정규화하는 방법도 있지만 질의마다 분포가 달라 까다롭다. 역순위 융합reciprocal rank fusion은 점수를 버리고 순위만 쓴다. 각 목록에서 순위 r인 문서에 1/(k + r)을 주고 더한다. 2009년 코맥 등이 제안했고, k = 60이 지금도 기본값으로 널리 쓰인다.

RRF(d) = Σ목록 i 1 / (k + ri(d))  ·  1위의 몫 : 10위의 몫 = (k + 10) : (k + 1)
k가 작으면 1위가 압도적으로 크고(한 목록의 1위가 이긴다), k가 크면 순위 차이가 평평해져 두 목록에 고르게 등장한 문서가 이긴다. k = 60이면 1위와 10위의 몫 차이는 1.15배에 불과하다.

색인 하나로 어디까지 버티나

카파시는 원천 백여 개, 페이지 수백 개 규모에서는 색인 파일 하나와 에이전트의 탐색만으로 임베딩 기반 검색 없이도 잘 돌아간다고 썼다. 그 경계를 계산해 보자. 색인은 페이지마다 한 줄(약 25토큰)이다. 질의마다 색인 전체를 읽는다면 색인이 컨텍스트에서 차지하는 몫이 문제다. 경계를 넘으면 두 가지 길이 있다. 색인을 분류별로 쪼개 맨 위 색인은 분류만, 분류 색인은 그 분류의 페이지만 담게 하거나, 검색 도구를 붙여 상위 결과만 읽는다.

핵심 정리

  1. 위키의 검색은 색인 → grep → BM25 → 임베딩 → 하이브리드·재순위화로 필요한 만큼만 올라간다.
  2. BM25는 정확한 용어, 고유명사, 숫자에 강하고, 임베딩은 바꿔 말한 표현과 뜻의 방향에 강하다.
  3. 두 결과는 점수가 아니라 순위로 합친다. 역순위 융합 1/(k + r), k = 60이 출발점이다.
  4. 평평한 색인은 수백 페이지에서 한계에 닿는다. 분류 색인으로 늘리고, 그 너머는 검색 도구를 붙인다.

확인 퀴즈

1. 오류 코드 “E-4012”가 나온 페이지를 찾을 때 가장 믿을 만한 것은?

숫자와 기호는 뜻의 방향이 거의 없다. 정확한 문자열 일치가 이긴다.

2. BM25의 b를 0으로 두면 생기는 일은?

b는 길이 정규화의 세기다. 0이면 긴 문서가 단어를 많이 담는 만큼 그대로 점수를 받는다.

3. 역순위 융합이 점수 합보다 나은 주된 이유는?

BM25와 코사인 유사도는 눈금이 다르다. 순위만 쓰면 그 문제가 사라진다.

4. 컨텍스트 창이 다섯 배 커지면 평평한 색인의 한계 페이지 수는?

색인 토큰은 페이지 수에 비례하므로 한계도 창 크기에 비례한다. 위키는 계속 자라고, 긴 입력의 가운데는 덜 읽힌다.
