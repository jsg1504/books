Chapter 01

에이전트 루프

채팅 모델은 질문 하나에 답 하나를 내놓는다. 코딩 에이전트는 같은 모델을 반복문 안에 넣는다. 모델이 도구 호출을 제안하면 하네스가 실행하고, 그 결과를 다시 모델에게 보여 준다. 이 단순한 반복이 왜 긴 작업을 가능하게 하는지, 그리고 언제 멈춰야 하는지를 수치로 확인한다.

  • 모델, 하네스, 도구, 환경이 각각 무엇을 책임지는지 구분할 수 있다.
  • 에이전트 루프의 한 턴이 어떤 메시지로 이루어지는지 트레이스에서 읽을 수 있다.
  • 피드백이 없는 연쇄 작업의 성공률 pn과 피드백 루프의 성공률을 비교할 수 있다.
  • 종료 조건(완료 선언, 턴 한도, 예산)의 설정이 결과 분포를 어떻게 바꾸는지 설명할 수 있다.

챗봇과 에이전트는 무엇이 다른가

같은 언어 모델이라도 쓰는 방식에 따라 전혀 다른 시스템이 된다. 채팅에서는 사용자의 질문과 모델의 답이 한 번 오간다. 답에 코드가 들어 있어도 그 코드를 실행해 보는 것은 사람의 몫이다. 코딩 에이전트coding agent는 모델에게 도구tool를 쥐여 주고, 모델이 도구를 부르면 프로그램이 대신 실행한 뒤 결과를 돌려준다. 모델은 그 결과를 보고 다음 행동을 고른다.

여기서 네 가지 역할을 구분해 두면 이후 장이 쉬워진다.

루프의 해부: 한 턴은 무엇으로 이루어지나

하네스의 핵심은 놀라울 만큼 짧다. 모델이 도구를 부르지 않는 답을 낼 때까지 호출과 실행을 반복한다.

agent_loop.py — 최소 하네스의사 코드
def run(task):
    messages = [{"role": "user", "content": task}]
    for turn in range(MAX_TURNS):               # 종료 조건 ①: 턴 한도
        reply = model(system, tools, messages)      # 컨텍스트 전체를 매번 다시 보낸다
        messages.append(reply)
        calls = [b for b in reply.content if b.type == "tool_use"]
        if not calls:                               # 종료 조건 ②: 도구 호출 없음 = 완료 선언
            return reply.text
        results = [execute(c) for c in calls]      # 권한 확인 → 실행 → 출력 자르기
        messages.append({"role": "user", "content": results})
    return "턴 한도에 도달했습니다"

모델에게 보내는 입력은 매 턴 시스템 프롬프트 + 도구 정의 + 지금까지의 모든 메시지다. 모델은 상태를 기억하지 않는다. 기억처럼 보이는 것은 하네스가 매번 다시 보여 주는 대화 기록이다. 이 사실이 2장(컨텍스트)과 9장(비용)의 출발점이 된다.

아래 재생기는 실제 에이전트가 남기는 형태의 트레이스를 한 단계씩 보여 준다. 과제는 “로그인 세션이 만료되지 않는 버그를 고쳐 줘”다. 오른쪽 그림에서 지금 어느 역할이 일하고 있는지, 컨텍스트가 얼마나 불어나는지 지켜보자.

왜 루프가 강력한가: 오류는 연쇄된다

버그 하나를 고치려면 여러 단계를 거친다. 관련 파일을 찾고, 원인을 짚고, 수정하고, 다른 곳이 깨지지 않았는지 확인한다. 각 단계를 성공률 p로 해낸다고 하자. 중간 확인 없이 n단계를 이어 붙이면 전체가 성공할 확률은 다음과 같다.

Popen = pn
p = 0.95, n = 20이면 0.9520 ≈ 0.36. 단계마다 95%로 잘해도 스무 단계짜리 일은 셋 중 둘이 실패한다.

피드백 루프는 실패를 발견하고 다시 시도할 기회를 준다. 한 단계가 실패했을 때 그 실패가 관찰(테스트 결과, 오류 메시지)로 드러날 확률을 d, 드러난 실패를 다시 시도할 수 있는 횟수를 r이라 하자. 단계 하나의 실효 성공률은 기하급수의 합이 된다.

q = p · 1 − ((1−p)d)r+11 − (1−p)d,    Ploop = qn
시도마다 성공하면 끝나고, 실패가 드러나면(확률 d) 재시도한다. 드러나지 않은 실패는 조용히 남아 과제 전체를 망친다. d = 0이면 q = p로 피드백이 없는 경우와 같다.

해볼 것: ① d = 0으로 두면 재시도를 아무리 늘려도 두 곡선이 겹친다 — 실패를 볼 수 없으면 고칠 수도 없다. ② d를 0.5 → 0.95로 올리면 "50% 한계 길이"가 몇 배로 늘어난다. 테스트를 잘 갖춘 저장소에서 에이전트가 훨씬 길게 일할 수 있는 이유다(6장).
모델은 같아도 하네스가 다르면 결과가 다르다위 식에서 p는 주로 모델의 능력이지만, d와 r은 하네스와 환경이 결정한다. 테스트를 실행할 수 있는가, 오류 메시지를 잘리지 않게 보여 주는가, 재시도할 턴이 남아 있는가. 같은 모델의 점수가 하네스마다 달라지는 이유가 여기에 있다.

언제 멈추는가: 종료 조건

루프는 반드시 끝나야 한다. 실무 하네스는 보통 여러 종료 조건을 함께 둔다.

  • 완료 선언 — 모델이 도구 호출 없이 최종 답을 낸다. 가장 흔한 종료이며, 모델이 너무 일찍 완료를 선언하는 것이 대표적인 실패다.
  • 턴 한도 — 무한 반복을 막는다. 너무 낮으면 풀 수 있는 문제를 중간에 끊는다.
  • 예산 — 토큰, 비용, 시간 한도. 긴 작업일수록 컨텍스트가 커져 한 턴의 비용도 커진다.
  • 사람의 개입 — 권한 요청에 대한 거부, 사용자의 중단.

아래 실험은 같은 과제를 200번 돌린 결과를 한 줄씩 그린다. 각 줄은 한 번의 실행이고, 칸 하나가 한 턴이다. 칸의 색은 그 턴의 행동이고, 줄 끝의 표시는 결과다. 에이전트는 매 턴 조금씩 진척하지만, 진척이 덜 된 상태에서 “다 했다”고 선언해 버릴 위험도 있다.

루프 설계의 다이얼

같은 루프 구조 안에서도 하네스는 여러 다이얼을 돌릴 수 있다. 이후 장은 이 다이얼 하나하나를 다룬다.

핵심 정리

  1. 코딩 에이전트 = 모델 + 도구 + 하네스의 반복문. 모델은 호출을 요청하고, 하네스가 실행하고 결과를 대화에 붙인다.
  2. 모델은 상태가 없다. 매 턴 시스템 프롬프트, 도구 정의, 전체 대화를 다시 입력받는다. 그래서 누적 입력 토큰은 현재 컨텍스트보다 훨씬 빨리 커진다.
  3. 피드백 없는 연쇄 작업의 성공률은 pn으로 무너진다. 실패를 드러내는 관찰(d)과 재시도 여유(r)가 긴 작업의 한계 길이를 늘린다.
  4. 종료 조건은 비용과 정확도를 맞바꾼다. 턴 한도가 낮으면 미완성, 조기 완료 선언은 오답, 완료 전 검증은 둘 다 줄인다.

확인 퀴즈

1. 모델이 도구를 “호출”할 때 실제로 명령을 실행하는 주체는?

모델은 도구 이름과 인자를 담은 요청 메시지를 생성할 뿐이다. 하네스가 권한을 확인하고 실행한 뒤 결과를 다음 입력에 붙인다.

2. 단계 성공률 0.9인 10단계 작업을 피드백 없이 수행할 때 전체 성공률에 가장 가까운 것은?

0.910 ≈ 0.349. 단계가 늘수록 성공률은 곱해져서 빠르게 떨어진다.

3. 실패 감지율 d가 0일 때 재시도 횟수 r을 늘리면?

실패가 관찰되지 않으면 재시도가 일어나지 않는다. q = p가 되어 피드백 없는 경우와 같다.

4. “완료 전 테스트 실행” 습관이 직접 줄이는 실패 유형은?

검증이 미완성을 드러내면 에이전트는 완료를 선언하지 않고 계속 작업한다. 대신 턴을 더 쓰므로 한도 초과는 약간 늘 수 있다.
