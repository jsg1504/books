Chapter 03

도구 호출

모델은 텍스트만 만든다. 파일을 읽거나 테스트를 돌리려면 도구 호출tool use, function calling이라는 약속이 필요하다. 하네스가 “이런 함수들이 있다”고 알려 주면, 모델은 그중 하나를 골라 인자를 채운 구조화된 요청을 만든다. 이 장에서는 그 요청이 어떻게 생겼는지, 잘못된 요청을 어떻게 걸러내는지, 여러 호출을 한 번에 보내면 무엇이 빨라지는지, 그리고 긴 결과를 어떻게 줄여 돌려줄지를 다룬다.

  • 도구 정의(이름, 설명, 입력 스키마)와 도구 호출·도구 결과 메시지의 구조를 설명할 수 있다.
  • 스키마 검증으로 잡을 수 있는 오류와 잡을 수 없는 오류를 구분할 수 있다.
  • 독립적인 호출을 병렬로 보낼 때 줄어드는 시간과 모델 호출 수를 계산할 수 있다.
  • 긴 도구 출력을 자르는 전략(앞, 뒤, 앞+뒤, 관련 줄)의 장단점을 비교할 수 있다.

도구는 함수 시그니처다

도구 정의는 세 부분으로 이루어진다. 이름은 모델이 호출할 때 쓰는 식별자, 설명은 언제 어떻게 쓰는지에 대한 자연어 안내, 입력 스키마는 JSON Schema로 적은 인자 형식이다. 모델은 설명을 읽고 도구를 고르며, 스키마를 보고 인자를 채운다. 설명이 곧 사용 설명서다.

도구 정의 — 하네스가 모델에게 보내는 것JSON
{
  "name": "read_file",
  "description": "저장소의 텍스트 파일을 읽는다. 큰 파일은 offset/limit으로 필요한 줄만 읽을 것.
                  결과의 각 줄 앞에는 줄 번호가 붙는다.",
  "input_schema": {
    "type": "object",
    "properties": {
      "path":   { "type": "string",  "description": "저장소 루트 기준 경로" },
      "offset": { "type": "integer", "minimum": 1 },
      "limit":  { "type": "integer", "minimum": 1, "maximum": 2000 }
    },
    "required": ["path"]
  }
}

한 번의 호출은 모델 응답 안의 tool_use 블록으로 나타나고, 하네스는 실행 결과를 같은 id를 가진 tool_result 블록으로 돌려준다. 실행이 실패하면 오류 메시지를 결과로 돌려주어 모델이 스스로 고치게 한다.

호출을 검증하기

모델이 만든 호출이 항상 올바르지는 않다. 없는 도구 이름, 빠진 필수 인자, 문자열로 쓴 숫자, 허용 범위를 넘는 값이 나올 수 있다. 하네스는 실행 전에 스키마로 검증하고, 실패하면 is_error가 표시된 결과로 무엇이 틀렸는지 알려 준다. 좋은 오류 메시지는 모델이 다음 턴에 바로 고칠 수 있게 한다.

아래 작업대에서 직접 모델 역할을 해 보자. 왼쪽 JSON을 고치고 실행을 누르면 하네스가 검증하고 가상의 저장소에서 실행한다.

병렬 도구 호출

세 파일을 읽어야 하는데 각 읽기가 서로 독립적이라면, 한 턴에 하나씩 세 턴에 걸쳐 읽을 이유가 없다. 모델은 한 응답 안에 여러 tool_use 블록을 담을 수 있고, 하네스는 이들을 동시에 실행할 수 있다. 줄어드는 것은 두 가지다. 벽시계 시간(도구 지연이 겹친다)과 모델 호출 수(매 호출마다 전체 컨텍스트를 다시 읽는 비용).

T순차 = k(tm + t̄tool) + tm   vs   T병렬 = tm + maxi ttool,i + tm
k: 독립 호출 수, tm: 모델 한 번의 응답 시간, ttool: 도구 실행 시간. 마지막 tm은 결과를 읽고 다음 행동을 정하는 턴이다.

긴 출력을 돌려주는 법

테스트 스위트를 돌리면 수천 줄의 로그가 나온다. 이것을 그대로 컨텍스트에 넣으면 윈도우를 순식간에 채우고(2장), 정작 중요한 실패 메시지는 중간에 묻힌다. 하네스는 결과에 토큰 한도를 두고 넘치는 부분을 자른다. 어떻게 자르느냐에 따라 모델이 원인을 볼 수 있는지가 갈린다.

좋은 도구의 조건

도구는 모델이 쓰는 API다. 사람이 쓰는 API와 같은 원칙이 적용되지만, 사용자가 문서를 매번 처음부터 읽는다는 점이 다르다.

외부 서비스(이슈 트래커, 데이터베이스, 브라우저)의 도구를 표준 방식으로 붙이기 위한 규약도 있다. MCPModel Context Protocol는 도구를 제공하는 서버와 그것을 쓰는 하네스 사이의 공통 인터페이스를 정한다. 하네스는 MCP 서버에서 도구 목록을 받아 모델에게 보여 주고, 호출을 서버로 중계한다.

핵심 정리

  1. 도구 = 이름 + 설명 + JSON 스키마. 모델은 tool_use로 호출을 요청하고, 하네스가 실행해 같은 id의 tool_result로 돌려준다.
  2. 스키마 검증은 형식 오류(누락, 타입, 범위)를 잡는다. 의미 오류(없는 파일, 모호한 편집)는 실행 단계에서 구체적인 오류 메시지로 알려야 한다.
  3. 독립적인 호출은 한 응답에 묶어 병렬로. 벽시계 시간과 모델 호출 수가 모두 준다.
  4. 긴 출력은 반드시 자른다. 앞+뒤 또는 관련 줄 추출이 실패 정보를 보존하는 데 유리하고, 가장 좋은 방법은 애초에 범위를 좁혀 실행하는 것이다.

확인 퀴즈

1. {"name":"read_file","input":{"limit":"50"}}에서 스키마 검증이 잡아내는 문제를 모두 고르면?

path는 required이고 limit은 integer여야 한다. 문자열 "50"은 타입 오류다.

2. 스키마 검증을 통과했는데 실행에서 실패할 수 있는 경우는?

나머지 둘은 검증 단계에서 걸린다. 경로의 존재 여부는 실행해 봐야 안다.

3. 모델 응답 4초, 도구 지연 1초, 독립 호출 4개. 병렬로 보내면 순차 대비 대략 몇 배 빠른가?

순차 4×(4+1)+4 = 24초, 병렬 4+1+4 = 9초. 24/9 ≈ 2.7.

4. 실패 메시지가 로그의 한가운데에 있고 끝에 요약 줄이 있다. “앞부분만” 전략의 문제는?

앞부분에는 보통 설치·수집 메시지가 있다. 한도가 작으면 실패 위치와 요약까지 닿지 못한다.
