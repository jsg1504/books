Chapter 08

병렬 에이전트와 오케스트레이션

에이전트 하나가 일하는 동안 사람은 기다린다. 그렇다면 다섯 개를 동시에 돌리면 다섯 배 빨라질까? 터미널을 여러 개 열고, git 워크트리로 작업 공간을 나누고, 원격의 백그라운드 에이전트에게 이슈를 던지는 방식이 빠르게 퍼졌다. 그런데 에이전트가 늘어도 사람은 한 명이다. 모든 작업은 결국 누군가 설명을 쓰고, 질문에 답하고, 결과를 읽고, 합쳐야 끝난다. 이 장에서는 병렬 에이전트의 진짜 병목이 어디인지 대기열 이론으로 보고, 작업끼리의 충돌과 주의 전환 비용을 잰다.

  • 리틀의 법칙과 사람의 처리 용량으로 병렬 에이전트의 처리량 상한을 계산할 수 있다.
  • 병렬 작업 수와 파일 겹침에 따른 충돌 확률을 어림하고 워크트리·작업 분리로 줄일 수 있다.
  • 주의 전환 비용을 줄이는 몰아서 확인하기의 득실을 설명할 수 있다.

병렬로 돌리는 방법

병렬 에이전트를 운영하는 방식은 크게 셋이다. 여러 대화형 세션(터미널이나 IDE 창마다 에이전트 하나), 워크트리 격리(git worktree로 브랜치마다 작업 디렉터리를 따로 꺼내 에이전트끼리 파일을 밟지 않게 함), 백그라운드 에이전트(원격 환경에서 일하고 PR로 결과를 돌려줌). 셋 모두 사람의 역할을 바꾼다. 타자를 치는 사람에서 일을 나눠 주고 결과를 검수하는 사람으로.

처리량 ≤ min( n / (G + 대기),   1 / (B + R) )  ·  리틀의 법칙: L = λ · W
n: 에이전트 수, G: 에이전트가 작업 하나에 쓰는 시간, B: 사람이 브리프 하나를 쓰는 시간, R: PR 하나를 리뷰하는 시간. 에이전트를 아무리 늘려도 하루 처리량은 사람의 B + R로 정해진 상한을 넘지 못한다. 그 상한에 가까워지면 대기열 길이 L과 대기 시간 W가 함께 폭발한다.

병렬 작업의 충돌

에이전트 둘이 같은 파일을 고치면 병합 충돌이 난다. 워크트리는 작업 중에 서로의 파일을 밟지 않게 해 주지만, 합칠 때의 충돌까지 없애지는 못한다. 충돌 확률은 생일 문제와 같은 구조다. 작업 하나가 건드리는 파일이 적어도, 작업 수가 늘면 어느 두 작업이 겹칠 확률은 빠르게 커진다. 게다가 실제 저장소에는 모두가 건드리는 핫스폿(라우터, 설정 파일, 공용 타입)이 있다.

주의 전환 비용

에이전트는 일하다가 사람을 부른다. “이 파일을 지워도 될까요?”, “두 방법 중 무엇이 좋을까요?”, “테스트 명령이 뭔가요?” 질문 하나에 답하는 데는 1–2분이면 되지만, 그 세션의 맥락을 머릿속에 다시 올리는 데는 몇 분이 더 든다. 에이전트가 다섯이면 사람은 하루 종일 맥락을 갈아 끼운다. 대안은 몰아서 확인하기다. 정해진 간격마다 모든 세션을 한 바퀴 돌며 쌓인 질문에 한꺼번에 답한다. 전환 비용은 줄지만 에이전트는 다음 순회까지 기다린다.

핵심 정리

  1. 병렬 에이전트의 처리량 상한은 에이전트 수가 아니라 사람의 브리프·리뷰 시간으로 정해진다. 상한 근처에서 대기열은 폭발한다(L = λW).
  2. 처리량을 올리려면 사람의 일을 줄인다. 자동 검증, 작은 diff, 재사용 가능한 명세와 규칙 파일이 그 레버다.
  3. 동시 작업이 늘면 충돌 확률은 쌍의 수만큼 빠르게 오르고, 핫스폿이 이를 키운다. 영역을 나누고 핫스폿 작업은 하나씩 돌린다.
  4. 에이전트가 부를 때마다 사람은 맥락 전환 비용을 낸다. 많이 돌릴수록 몰아서 확인하기가 유리하다.

확인 퀴즈

1. 브리프 5분, 리뷰 15분이 드는 작업을 사람 한 명이 하루 8시간 처리한다. 에이전트를 무한히 늘려도 넘지 못하는 하루 처리량은?

480분 ÷ (5 + 15)분 = 24개. 사람이 작업 하나에 쓰는 시간이 상한을 정한다.

2. 리뷰 대기열에 평균 6개 PR이 있고 하루 12개가 들어온다면 PR 하나의 평균 대기 시간은?

리틀의 법칙 W = L / λ = 6 / 12 = 0.5일.

3. 워크트리를 쓰면 병합 충돌이 사라질까?

워크트리는 작업 공간을 나눌 뿐이다. 겹치는 변경은 병합 시점에 드러난다.

4. 에이전트 여덟 개가 수시로 질문을 해 사람이 하루 종일 창을 오간다. 가장 효과적인 개선은?

질문 빈도와 전환 비용을 함께 줄여야 유효 에이전트 수가 늘어난다.
