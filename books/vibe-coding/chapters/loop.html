Chapter 02

루프의 해부: 프롬프트에서 커밋까지

AI와 코딩하는 일은 결국 한 바퀴의 반복이다. 말하고, 에이전트가 만들고, 돌려 보고, 결과를 보고, 다시 말한다. 바이브 코딩과 에이전틱 엔지니어링은 같은 바퀴를 돈다. 다른 것은 한 바퀴에 무엇을 확인하느냐와 한 바퀴가 얼마나 빠르냐다. 이 장에서는 바퀴의 속도가 완료 시간을 어떻게 지배하는지, 확인을 건너뛴 바퀴가 어떻게 숨은 고장을 쌓는지, 그리고 바퀴가 제자리에서 헛돌 때 어떻게 빠져나오는지를 본다.

  • 피드백 루프의 한 바퀴 시간이 전체 완료 시간과 성공 확률을 어떻게 바꾸는지 계산할 수 있다.
  • 읽지 않고 수락한 변경이 쌓일 때 “아무것도 깨지지 않았을 확률”이 얼마나 빨리 줄어드는지 설명할 수 있다.
  • 둠 루프의 징후를 알아보고, 새 세션·사람의 힌트 같은 탈출 전략을 고를 수 있다.

한 바퀴의 네 단계

모든 AI 코딩 세션은 네 단계를 반복한다. 사람이 의도를 말하고, 에이전트가 코드를 생성하고, 무언가가 그 코드를 실행하고, 누군가가 결과를 관찰해 다음 의도를 정한다. 코딩 에이전트는 이 바퀴의 상당 부분을 스스로 돈다. 테스트를 실행하고 오류를 읽고 다시 고친다. 사람이 끼어드는 지점이 적을수록 바퀴는 빨라진다. 대신 사람이 끼어들지 않은 바퀴에서는 무엇이 확인되었는지를 실행 단계가 전부 결정한다.

완료까지 바퀴 수 N ~ 음이항(k, p)  ·  E[N] = k / p  ·  E[시간] = (k / p) · (g + c)
k: 고쳐야 할 문제 수, p: 한 바퀴에서 문제 하나를 해결할 확률, g: 생성 시간, c: 확인 시간. 실패한 바퀴도 시간을 쓴다. 그래서 p가 낮을수록 c의 차이가 크게 벌어진다.

전부 수락의 표류

바이브 코딩의 핵심 습관은 전부 수락accept all이다. 변경이 동작하는 것처럼 보이면 diff를 읽지 않고 받아들인다. 문제는 “동작하는 것처럼 보인다”가 지금 보고 있는 기능에 대한 판단이라는 점이다. 이번 변경이 세 화면 떨어진 다른 기능을 깨뜨렸는지는 보이지 않는다.

P(숨은 고장 없음) = (1 − q · (1 − c))n   ·   예: q = 0.1, c = 0, n = 20 → 0.920 ≈ 0.12
q: 변경 하나가 다른 기능을 조용히 깨뜨릴 확률, c: 그 고장을 자동 테스트나 리뷰가 바로 잡을 확률, n: 수락한 변경 수. 하나하나는 90% 안전해도 스무 번 연속이면 88% 확률로 어딘가 깨져 있다.

둠 루프에서 빠져나오기

바이브 코딩을 해 본 사람은 다 아는 장면이 있다. 오류를 붙여 넣는다. 에이전트가 “이제 고쳤습니다”라고 한다. 같은 오류가 난다. 다시 붙여 넣는다. 다른 곳을 고친다. 처음 오류가 돌아온다. 이것이 둠 루프doom loop다. 원인은 대개 둘이다. 에이전트가 원인 대신 증상을 고치고 있거나, 컨텍스트에 쌓인 실패한 시도들이 다음 시도를 같은 방향으로 끌고 가는 것이다.

징후뜻대응
같은 오류 메시지가 세 번째증상을 돌려막는 중멈추고 “원인 가설 세 개와 확인 방법”을 먼저 요청
고친 곳이 매번 다르다문제의 위치를 모른다재현 테스트를 먼저 쓰게 한다 (5장)
답변이 점점 길고 확신에 차 있다컨텍스트가 실패로 오염됨요약만 들고 새 세션 (4장)
테스트를 고치거나 지우자고 한다목표 대신 검사를 통과하려 함즉시 중단, 테스트는 사람이 지킨다 (5장)

아래 실험에서 에이전트의 성공 확률은 컨텍스트에 실패한 시도가 쌓일수록 줄어든다(“오염”). 세 가지 전략을 각 2,000번씩 돌려 비교한다.

핵심 정리

  1. AI 코딩은 의도–생성–실행–관찰의 반복이다. 한 바퀴 시간은 생성 시간과 확인 시간의 합이고, 완료 시간은 대략 (k/p) × 한 바퀴다.
  2. 자동 테스트는 확인 시간을 초 단위로 줄여 에이전트가 스스로 바퀴를 돌게 한다. 테스트는 품질 장치이기 전에 속도 장치다.
  3. 읽지 않고 수락한 변경의 회귀는 곱으로 쌓인다. 0.920 ≈ 0.12. 테스트와 리뷰는 서로 다른 빈틈을 메운다.
  4. 같은 오류를 맴돌면 멈춘다. 원인 가설을 묻고, 재현 테스트를 먼저 쓰고, 그래도 안 되면 요약만 들고 새 세션을 연다.

확인 퀴즈

1. 고칠 문제가 4개, 바퀴당 해결 확률 0.5, 한 바퀴 2분이면 기대 완료 시간은?

기대 바퀴 수는 k/p = 4/0.5 = 8, 바퀴당 2분이니 16분이다.

2. 변경마다 5%의 확률로 다른 기능을 조용히 깨뜨린다면, 읽지 않고 30번 수락한 뒤 아무것도 안 깨졌을 확률은 대략?

0.9530 ≈ 0.215. 작은 확률도 곱해지면 금방 커진다.

3. 에이전트가 같은 오류를 세 번째 고치고 있다. 가장 먼저 할 일은?

같은 증상을 돌려막는 중이다. 원인을 먼저 좁혀야 한다. 테스트를 지우는 것은 문제를 숨길 뿐이다.

4. 실패한 시도가 컨텍스트에 쌓여 다음 시도를 오염시킨다면, 새 세션이 도움이 되는 이유는?

컨텍스트는 에이전트의 작업 기억이다. 틀린 시도로 가득 찬 기억은 다음 시도를 같은 방향으로 끌고 간다.
