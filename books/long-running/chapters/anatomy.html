Chapter 02

긴 실행의 해부: 안쪽 루프와 바깥 루프

모든 에이전트의 심장은 같은 루프다. 모델이 다음 행동을 고르고, 하네스가 도구를 실행하고, 결과가 다시 모델에게 돌아간다. 장기 실행 에이전트는 이 루프를 한 겹 더 감싼다. 창이 차거나 세션이 끝나면, 바깥 루프가 상태를 파일에 적고 새 창에서 같은 일을 이어 가게 한다. 이 장에서는 두 루프의 구조와, 바깥 루프를 잘 돌리기 위한 가장 중요한 습관 두 가지 — 초기화를 따로 하기와 한 세션에 기능 하나 — 를 본다.

  • 안쪽 루프와 바깥 루프를 구별하고, 각 루프가 무엇을 기억하고 무엇을 잊는지 설명할 수 있다.
  • 초기화 세션이 준비해야 하는 것(기능 목록, 진행 파일, 실행 스크립트, git)을 나열할 수 있다.
  • 한 번에 다 하려는 전략이 왜 “다 했다는데 절반이 안 되는” 결과를 낳는지 모형으로 설명할 수 있다.

루프 속의 루프

안쪽 루프inner loop는 한 컨텍스트 창 안에서 돈다. 모델 호출 → 도구 실행 → 결과를 창에 덧붙이기 → 다시 모델 호출. 이 루프의 기억은 창 그 자체다. 창이 커질수록 모델은 더 많은 것을 알지만, 언젠가 창은 가득 찬다.

바깥 루프outer loop는 세션 단위로 돈다. 한 세션이 끝나면 새 프로세스가 빈 창으로 시작해 같은 목표를 이어 받는다. 이 루프의 기억은 디스크다. 진행 파일, 기능 목록, git 기록, 테스트 결과. 가장 단순한 바깥 루프는 셸 한 줄이다. 같은 프롬프트를 에이전트에 끝없이 다시 넣는 이 방식은 개발자 제프리 헌틀리가 소개한 뒤 랄프 루프Ralph loop라는 이름으로 퍼졌다.

outer-loop.sh
while true; do
  cat PROMPT.md | agent --print   # 새 창, 같은 지시
  # 상태는 저장소에만 남는다: progress.md, features.json, git log
done

이 한 줄이 동작하는 이유는 PROMPT.md가 “먼저 progress.md와 git log를 읽고, 끝나지 않은 가장 중요한 일 하나를 골라, 끝내고, 테스트하고, 커밋하고, progress.md를 갱신하라”고 말하기 때문이다. 바깥 루프의 지능은 루프 코드가 아니라 매 세션이 남기고 읽는 파일의 질에 있다.

안쪽 원을 한 바퀴 도는 것이 한 턴(모델 → 도구 → 관찰)이다. 창(청록 막대)이 가득 차면 에이전트가 보라 상자(진행 파일·git)에 상태를 적고 바깥 고리를 따라 새 세션으로 넘어간다. 새 세션의 첫 몇 턴은 그 파일을 읽는 데 쓰인다(보라 턴). 해볼 것: ① 창을 50K로 줄이면 세션이 잦아지고 시작 비용의 비율이 커진다. ② 시작 비용을 60K로 올리면(진행 파일이 엉망이라 코드를 다 뒤져야 하는 상황) 창의 상당 부분이 재적응에 쓰인다. 진행 파일의 질이 곧 처리량이다(4장).

초기화 세션과 한 세션에 기능 하나

Anthropic은 2025년 말 긴 시간 동안 웹 앱을 만드는 코딩 에이전트의 하네스를 공개하면서, 처음에 에이전트가 빠지던 실패를 정리했다. 하나는 한 번에 다 하려는 것이다. 에이전트는 첫 세션부터 앱 전체를 단숨에 만들려다 창이 끝나고, 다음 세션은 반쯤 만들어지고 설명도 없는 코드를 물려받아 무슨 일이 있었는지 추측하는 데 시간을 썼다. 다른 하나는 때 이른 완료 선언이다. 몇 세션 뒤 들어온 에이전트가 진척을 보고는 “다 됐다”고 선언해 버렸다.

해결책은 역할을 나누는 것이었다. 첫 세션의 초기화 에이전트initializer agent는 코드를 쓰기 전에 환경을 만든다. 사용자의 요구를 수백 개의 검사 가능한 기능으로 풀어 모두 “실패”로 표시한 기능 목록, 무엇을 했는지 적을 진행 파일, 개발 서버를 띄우는 init.sh, 첫 git 커밋. 이후 세션의 코딩 에이전트는 매번 기능 하나만 골라 끝내고, 브라우저 자동화로 사용자처럼 확인하고, 커밋하고, 진행 파일을 갱신한다.

모형: 점진 전략은 기능마다 테스트(구현의 25%)를 하고, 잡은 버그는 바로 고친다(싸다). 세션 끝에 끝내지 못한 기능은 되돌려 깨끗한 상태로 넘긴다. 한 번에 전략은 테스트 없이 20% 빨리 쓰지만, 다음 세션은 반쯤 만든 코드를 파악하느라 6턴을 더 쓰고, 숨은 버그는 세션마다 20%만 우연히 드러나며, 그것을 고치는 비용은 테스트되지 않은 코드가 많을수록 커진다. 그리고 모든 기능을 썼다고 생각하는 순간 완료를 선언한다. 해볼 것: ① 기본값에서 “한 번에”는 한 세션 먼저 40/40을 보고하지만 실제로 통과하는 기능은 30개 초반이다. ② 버그 확률을 0으로 내리면 “한 번에”가 이긴다. 그런 세상은 없다. ③ 테스트 포착률을 0으로 내리면 점진 전략도 숨은 버그를 안고 끝난다. 쪼개기만으로는 부족하고 확인이 함께 가야 한다(7장).

새 세션의 첫 다섯 수

바깥 루프의 매 세션은 기억이 없는 사람이 교대 근무를 시작하는 것과 같다. 인수인계 메모를 먼저 읽고, 장비가 정상인지 확인하고, 그다음에야 일을 시작한다. 순서가 틀리면 앞 세션이 남긴 고장 위에 새 기능을 쌓게 된다.

핵심 정리

  1. 안쪽 루프의 기억은 컨텍스트 창, 바깥 루프의 기억은 디스크다. 장기 실행은 둘을 잇는 설계다.
  2. 가장 단순한 바깥 루프는 같은 프롬프트를 계속 넣는 셸 한 줄이다. 지능은 루프가 아니라 매 세션이 읽고 남기는 파일에 있다.
  3. 초기화 세션은 코드보다 환경을 먼저 만든다. 모두 실패로 표시된 기능 목록, 진행 파일, 실행 스크립트, 첫 커밋.
  4. 한 세션에 기능 하나. 끝내고, 확인하고, 커밋하고, 기록한다. 한 번에 다 하려는 전략은 빨라 보이지만 반쯤 만든 코드와 숨은 버그와 때 이른 완료 선언을 남긴다.

확인 퀴즈

1. 바깥 루프에서 세션과 세션 사이에 상태를 넘겨 주는 것은?

새 세션은 빈 창으로 시작한다. 이어지는 것은 저장소에 남긴 것뿐이다.

2. 초기화 세션이 기능 목록의 모든 항목을 “실패”로 표시해 두는 이유는?

남은 일이 목록에 실패로 남아 있으면 “다 된 것 같다”는 느낌이 아니라 목록이 완료를 판정한다.

3. 세션이 끝날 무렵 기능 하나를 70%까지 만들었다. 점진 전략에서 가장 알맞은 행동은?

다음 세션이 설명 없는 반쪽 코드를 물려받으면 추측하는 데 시간을 쓴다. 넘겨줄 때는 항상 깨끗한 상태와 분명한 메모로.

4. 새 코딩 세션이 기능 구현보다 먼저 기본 흐름 테스트를 돌리는 이유는?

고장은 생긴 직후에 가장 싸게 고친다. 새 기능을 얹은 뒤에는 원인을 찾기가 훨씬 어렵다.
