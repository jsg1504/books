Chapter 05

체크포인트, 재개, 멱등성

8시간짜리 실행이라면 그 사이 무언가는 죽는다. API가 시간 초과로 끊기고, 컨테이너가 재배치되고, 노트북 뚜껑이 닫힌다. 장기 실행 에이전트의 질문은 “죽지 않게 하려면?”이 아니라 “죽은 뒤 어디서부터, 무엇을 두 번 하지 않고 이어 갈까?”다. 이 장에서는 체크포인트를 얼마나 자주 남길지, 재개할 때 바깥 세상에 한 일을 어떻게 두 번 하지 않을지, 그리고 이 문제를 체계적으로 푸는 내구 실행을 본다.

  • 저장 비용과 고장 빈도로 최적 체크포인트 간격을 어림할 수 있다(영의 공식).
  • 재개할 때 외부 부작용이 중복되는 이유와, 멱등 키로 막는 방법을 설명할 수 있다.
  • 이벤트 로그를 재생해 같은 지점으로 돌아가는 내구 실행의 원리와, 워크플로 코드가 결정적이어야 하는 이유를 말할 수 있다.

얼마나 자주 저장할까

체크포인트checkpoint는 되살릴 수 있게 저장한 지점이다. 코딩 에이전트에게는 테스트가 통과한 git 커밋이 가장 흔한 체크포인트다. 체크포인트를 자주 남기면 충돌 때 잃는 일이 적지만, 남길 때마다 비용(테스트 실행, 커밋, 상태 직렬화)이 든다. 드물게 남기면 저장 비용은 적지만 충돌 한 번에 많이 잃는다. 1974년 존 영(John Young)은 이 균형점을 간단한 식으로 보였다. 고장이 평균 M분마다 무작위로 일어나고 저장에 C분이 든다면, 최적 간격은 대략 두 값의 곱의 제곱근이다.

τ* ≈ √(2 C M)  ·  기대 소요 = M eR/M (e(τ+C)/M − 1)
τ: 체크포인트 사이 작업 시간, C: 체크포인트 비용, M: 평균 고장 간격(MTBF), R: 충돌 뒤 재시작 비용(새 세션의 재적응 포함). 오른쪽은 고장이 포아송 과정일 때 작업 τ분을 끝내는 데 드는 기대 시간이다(데일리, 2006). 그래프는 이 정확한 식으로 그렸다.

두 번 보내진 이메일

저장소 안의 일은 되돌리고 다시 하면 그만이다. 하지만 에이전트가 바깥 세상에 한 일 — 이메일 발송, PR 생성, 결제, 슬랙 메시지, 클라우드 자원 예약 — 은 다시 하면 두 번 일어난다. 가장 위험한 순간은 외부 호출이 성공한 직후, 그 사실을 기록하기 직전에 죽는 것이다. 재개한 에이전트는 기록이 없으니 같은 호출을 다시 한다.

해법은 멱등성idempotency이다. 같은 일을 두 번 해도 한 번 한 것과 같게 만든다. 외부 호출마다 작업과 단계에서 정해지는 고유한 멱등 키idempotency key를 붙이고(예: run-42/step-6), 받는 쪽이 같은 키의 두 번째 요청을 무시하게 한다. 결제 API 다수가 이런 키를 지원한다. 키를 지원하지 않는 곳이라면 호출 전에 “보낼 예정”을, 호출 뒤에 “보냈음”을 기록하고, 재개할 때 “보낼 예정”만 있는 항목은 상대에게 확인한 뒤 진행한다.

GAME

충돌과 재개 — 어디서 죽었고, 무엇이 두 번 일어났나

에이전트가 버그를 고치고 PR을 올리는 여덟 단계 작업이다. 단계를 눌러 충돌 지점을 고르고(그 단계의 효과가 일어난 직후, 기록 직전에 죽는다), 재개 전략을 고른 뒤 실행해 보자. 먼저 리뷰어가 메일을 몇 통 받을지 예측해 보자.

중복된 외부 효과—
다시 한 단계—
GPU 예약 청구—
해볼 것: ① 6단계(메일 발송)에서 충돌시키고 “마지막 커밋에서 재개”를 고르면, 커밋은 3단계였으므로 4~6단계가 다시 실행된다. PR이 두 개, 메일이 두 통이다. ② “처음부터 다시”는 저장소 일까지 전부 다시 하고, 외부 효과도 전부 중복된다. ③ “이벤트 로그 + 멱등 키”는 완료된 단계를 로그에서 건너뛰고, 충돌한 단계만 같은 키로 다시 보낸다. 받는 쪽이 중복을 버리므로 외부 효과는 한 번씩만 일어난다.

내구 실행: 로그를 재생해 돌아오기

내구 실행durable execution은 위의 해법을 일반화한 실행 방식이다. 템포럴(Temporal) 같은 워크플로 엔진이 대표적이며, 최근에는 에이전트 프레임워크들도 비슷한 기능을 갖추고 있다. 원리는 이렇다. 워크플로 코드가 바깥 세상과 닿는 모든 호출(LLM 호출, 도구 실행, API 요청)을 활동으로 감싼다. 엔진은 활동의 결과를 이벤트 로그에 기록한다. 작업자가 죽으면 새 작업자가 워크플로 코드를 처음부터 다시 실행하되, 이미 로그에 있는 활동은 실제로 호출하지 않고 로그의 결과를 돌려준다. 로그가 끝나는 지점에 이르면 그때부터 실제 호출을 한다.

대가: 결정성재생이 같은 지점으로 돌아오려면 워크플로 코드가 결정적이어야 한다. 같은 로그를 받으면 같은 순서로 같은 활동을 불러야 한다. 현재 시각, 난수, 파일 시스템 상태로 분기하면 재생 때 다른 길로 가서 로그와 어긋난다. 그런 값도 활동으로 감싸 로그에 남겨야 한다. LLM 호출의 결과가 매번 다른 것은 문제가 아니다. 그 결과 자체가 로그에 남기 때문이다.

해볼 것: ① 몇 단계 진행한 뒤 충돌시키고 재개하면, 새 작업자가 코드를 처음부터 다시 돌지만 보라색 줄은 로그에서 결과만 읽어 순식간에 지나간다. 실제 호출 수는 늘지 않는다. ② “처음부터”를 누르고 비결정적 코드를 켠 뒤, 8번째 활동(push)까지 실행하고 충돌·재개해 보자. 재생하던 작업자가 다른 분기로 가서 로그와 어긋나는 오류가 난다.

핵심 정리

  1. 최적 체크포인트 간격은 대략 √(2 × 저장 비용 × 평균 고장 간격)이다. 끝에만 저장하는 긴 실행은 오버헤드가 폭발한다.
  2. 재시작 비용은 간격보다 오버헤드 전체를 올린다. 재적응을 싸게 만드는 외부 기억이 모든 충돌을 싸게 만든다.
  3. 저장소 안의 일은 다시 해도 되지만, 바깥 세상에 한 일은 두 번 일어난다. 외부 호출에는 멱등 키를 붙인다.
  4. 내구 실행은 활동의 결과를 로그에 남기고, 재개 때 코드를 재생해 같은 지점으로 돌아온다. 워크플로 코드는 결정적이어야 한다.

확인 퀴즈

1. 체크포인트 비용이 2분, 평균 고장 간격이 4시간(240분)이라면 영의 근사로 최적 간격은?

√(2 × 2 × 240) = √960 ≈ 31분.

2. 에이전트가 결제 API를 호출해 성공한 직후, 기록하기 전에 죽었다. 재개 때 중복 결제를 막는 가장 확실한 방법은?

기록과 호출 사이의 틈은 없앨 수 없다. 대신 같은 호출을 두 번 해도 한 번과 같게 만든다.

3. 내구 실행에서 워크플로 코드가 if (Math.random() < 0.5)로 분기하면 무엇이 문제인가?

재생은 같은 입력이면 같은 길로 간다는 가정에 기댄다. 난수도 활동으로 감싸 로그에 남겨야 한다.

4. LLM 호출의 결과가 매번 다르다면 내구 실행의 재생이 깨지는가?

비결정적인 것은 활동 안에 두고, 결과를 로그에 남기면 된다. 워크플로 코드 자체만 결정적이면 된다.
